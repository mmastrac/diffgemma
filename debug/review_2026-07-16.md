## Part 1 — E20 top-k attention

**Verdict: the win is real and the kernel design is sound. But it ships at k=64 with
no quality measurement at that k, it silently ignores the tuned `hc=16`, its stated
"next optimization" targets the wrong bottleneck, and it re-introduces an
atomic-compaction nondeterminism bug this repo already fixed once (`cd66294`).**

E20 is default-OFF, so its 1.19× is currently worth **zero in production**. Every
item below is really in service of one question: what has to be true to flip the
default on?

### 1.1 The stated "next optimization" is targeting the wrong bottleneck

`debug/sparse_attn_findings.md` ends with:

> The softmax (26% of top-k time) can be cut further by replacing the atomic-based
> histogram with per-thread local histograms + a single merge (eliminates atomic
> contention). Estimated ~2x reduction in softmax cost.

**That ~2× is arithmetically impossible — `attn_topk_softmax` is bandwidth-bound,
not atomic-bound.** Recomputing from the committed prod-shape bench (`7fcf3ff`:
canvas=1024, hc=4, 16 q-heads, hd=512, BN=64), the S plane is
`hc × m × n_pad × 4B × (16/hc)` per layer and the kernel reads it three times:

| kv | S plane | sm 3-pass traffic | sm time | **effective** | QK |
|---|---|---|---|---|---|
| 15000 | 1.05 GB | 3.16 GB | 25.37 ms | **124.5 GB/s** | 3.82 TF/s |
| 30000 | 2.03 GB | 6.10 GB | 51.88 ms | **117.6 GB/s** | 3.86 TF/s |
| 60000 | 4.00 GB | 12.00 GB | 100.43 ms | **119.5 GB/s** | 3.87 TF/s |

M3 Pro DRAM ≈ 150 GB/s. **sm runs at 78–83% of the memory wall, flat across kv** —
the signature of a bandwidth-saturated kernel. Removing *100%* of the atomic cost
caps out at 150 GB/s = 25.4 → 21 ms, i.e. **1.2× on sm = 4 ms of 102.6 ms attention
= ~4% on attention, ~1% end-to-end.** Not 2×.

(The QK column independently confirms the commit's own claim: QK really is pinned at
the ~3.8 TF/s half-MMA wall. That part of `7fcf3ff` is correct.)

### 1.2 The real sm lever: the three passes only ever read 16 bits

This is the juice. Read the kernel's three passes:

- Pass 1 (`attention_topk.metal:164`): uses `pat >> 24` — top 8 bits.
- Pass 2 (`:217`): uses `(pat >> 16) & 0xFF` — next 8 bits.
- Pass 3 (`:255-256`): `top16 = pat >> 16; if (top16 >= thresh_top16)` — top 16 bits.

**All three passes compare only the top 16 bits of the monotonic key.** The full f32
score is needed *only* for the ~64–96 winners that reach `p[slot] = s[t]` (`:259`).

So: have `attn_gemm_qk` also emit a `u16` pattern plane (top 16 bits of
`topk_float_to_key(s)`) alongside S. Then sm's three passes read **half the bytes**,
and pass 3 fetches f32 only for winners (negligible — ~64 of 16064 per row).

- sm traffic 3.16 GB → 1.58 GB → **25.4 ms → ~12.7 ms** (a true 2×, the one the doc
  wanted, via the right mechanism)
- attention 102.6 → 89.9 ms = **1.14×**; E20 vs E17 goes 2.13× → 2.43×
- QK pays +526 MB of writes but is compute-bound at 10% bandwidth utilization — free.
- **Bit-identical to today's E20.** The kernel already discards bits 0–15 in every
  comparison, so materializing only the top 16 changes nothing. That is a rare
  property for a perf change in this repo — no gate re-run needed beyond golden.

Stacking the doc's atomic fix on top of this gets sm to ~10.6 ms. Worth doing *after*,
not instead.

### 1.3 What about full fusion? — already answered by E18, don't re-litigate

The tempting next thought is "don't materialize S at all — fuse selection into QK,
flash-style." Ceiling would be attention = qk(70.4) + pv(4.4) = 74.8 ms = **1.37×**,
plus the entire S scratch (0.4 GiB at hc=4/100k) disappears.

**This is not reachable, and E18 already proved why.** Streaming top-k requires one
threadgroup to own a whole row's key range (running threshold + running top-k). That
is exactly flash's dataflow, and PLAN.md's E18 row records the structural verdict at
hd=512: `BQ=16` register cap → tiny MMA tiles → 3× slower than E17 even after the
device-load rewrite. QK's grid splits columns across `t_total/BN` = 251 threadgroups;
per-row partial top-64s would need a 251-way merge, putting you right back where you
started.

**Do not spend a cycle on fused QK+top-k at hd=512.** The E18 disproof transfers
cleanly. §1.2 is the version of this idea that actually fits the machine.

### 1.4 Nondeterminism — this is `cd66294` again, character for character

`attention_topk.metal:257-261`:

```c
uint slot = atomic_fetch_add_explicit(&emit_cnt, 1u, memory_order_relaxed);
if (slot < K_PAD) { p[slot] = s[t]; idx[slot] = t; }
```

then `attn_topk_pv:344-354` sums `acc0 += pj * vb[idx[j] ...]` in list order.

Compare `cd66294` ("fix(sc): deterministic sparse-softembed survivor order"):

> `sc_sparse_select` compacted survivors with `slot = atomic_fetch_add(&cnt, 1u)`, so
> the per-row survivor LIST was in run-to-run-varying race order. `sc_sparse_gather`
> then sums `acc += prob[j]*embed[idx[j]]` in list order — a non-associative f32
> reduction over a nondeterministic order.

Same compaction, same race, same non-associative f32 reduction over the resulting
order. That commit's fix was a **threadgroup count + exclusive prefix-sum** giving a
fixed thread-major order.

**E20's version is strictly worse than the SC one.** In SC only the *order* raced.
Here `if (slot < K_PAD)` means that when `emit_cnt > K_PAD`, **which keys survive** is
race-determined — the *set*, not just the order.

And overflow is not a corner case, it's the normal path. The threshold is chosen so
`count(top16 > thresh) < k ≤ count(top16 >= thresh)`; pass 3 emits *every* key with
`top16 >= thresh`, including all ties. Scores cluster in one exponent, so top16 varies
in ~7 mantissa bits = ~128 distinct values; at n_valid ≈ 16k that's ~125 keys per tie
bucket against k=64. **Emit routinely exceeds K_PAD=64 and truncates by race.**

Why the gate can't see it: the race only drops keys *at the threshold* — the smallest
of the selected set, contributing least after softmax. `cd66294`'s own message
predicted this exactly — *"Token output stayed stable for clean prompts (the diffs
don't move argmax), but borderline-convergence prompts flipped their early-stop step
count."* A 17/17 clean-prompt gate is blind to it by construction; it showed up as
smoketest step-count jitter.

**Cheap decisive test, protocol already established by `cd66294`:** run one prompt ×8
at the same seed and binary with `DGQ_ATTN_TOPK=1` and count distinct early-stop step
counts. Old code gave `5,6,7`; fixed gave `6,6,6...`. Do this before anything else —
it's ~10 minutes and it gates whether E20 can ship at all.

Fixes, cheapest first:
1. **Bitonic-sort the ≤64 `(score, idx)` pairs after emit** (one simdgroup, ~36
   compare-exchange steps, free). Fixes the *order* half → PV sum becomes
   reproducible.
2. **Count + exclusive prefix-sum** as in `cd66294` → deterministic *set*. Costs one
   extra pass over the pattern plane; §1.2's u16 plane more than pays for it
   (4 × 526 MB = 16.9 ms, still well under today's 25.4 ms **and** deterministic).
3. A third radix level (bits 8–15) narrows ties 256× so overflow becomes rare — the
   real fix if you want the kernel to actually compute top-k.

### 1.5 The comment claims exactness the kernel doesn't deliver

`mod.rs:249-250`:

> `// topk is exact (same selection + same renormalization); tolerance is for f16-KV
> // rounding + bf16 output rounding + bf16 Q rounding.`

Not true, per §1.4: the tie bucket is emitted wholesale and truncated by race. The
kernel computes *an arbitrary K_PAD-subset of a superset of the top-k*. The test
passes because the dropped keys are the least significant ones, not because the
selection is exact. `topk_k1_matches_argmax_value:264-268` *does* document the tie
behaviour — so the knowledge exists, it just didn't propagate to the k=64 test. Fix
the comment; it will mislead the next reader into trusting the wrong invariant.

Related coverage gap: `topk_recovers_dense` uses k ≥ n_valid (no truncation) and
`topk_k1` uses k=1 (bin refines to exact). **No test exercises the overflow/tie
regime** — which is the production regime. Worth a fixture with deliberately clustered
scores.

### 1.6 k=64 was never quality-measured, and `DGQ_ATTN_TOPK_K` can't raise it

The mass table in `sparse_attn_findings.md` **starts at k=128** (71% at pos 129, 85%
at pos 0). Production ships **k=64**, whose retained mass appears nowhere in the doc.
Mass is monotonic in k, so shipped k=64 sits *below* the lowest number anyone measured
— and the doc's own recommendation was the opposite: *"Prototype at k=512 (90% mass
avg). If quality passes, push k higher (1024, 2048)."*

Worse, the knob doesn't work:
- `flags.rs:442` parses `DGQ_ATTN_TOPK_K` (default 64)
- `step_kernel.rs:3331` — `attn_topk_k().min(K_PAD)`
- `mod.rs:28` — `pub const K_PAD: usize = 64`

So **`DGQ_ATTN_TOPK_K=512` is silently clamped to 64**. No warning. The one axis the
findings doc says to explore is unreachable from the flag.

And `tuned_source(bm, bn, sm_tpg, k_pad)` (`mod.rs:44`) — the machinery to vary K_PAD
— **is dead code in production**: `pipelines()` compiles `SHADER_TOPK` directly
(`mod.rs:69-70`), so BM/BN/SM_TPG/K_PAD are all frozen at their `#ifndef` defaults.
The tunable exists but nothing reaches it, and E20 is absent from the holistic BO
surface entirely.

**Caveat the doc misses — raising k is free in FLOPs but not in *this* PV kernel.**
The findings doc concludes "at long context all k values converge to ~50% FLOPs, so
pick the largest k that fits" and separately dismisses sparse-PV work ("PV is <1%; no
need for MMA-based sparse PV"). Those two conclusions are coupled and the doc treats
them as independent. `attn_topk_pv` is a scalar gather looping `j < K_PAD` on a single
32-thread simdgroup — **cost is linear in K_PAD**, not in FLOPs:

| | K_PAD=64 | K_PAD=512 (est.) |
|---|---|---|
| pv @ kv=15k | 4.4 ms | ~35 ms |
| attention total @ kv=15k | 102.6 ms | ~131 ms → **1.67×** vs E17 (from 2.13×) |
| attention total @ kv=100k | ~610 ms | ~675 ms → **~2.15×** vs E17 (barely moves) |

So the "PV is negligible, don't bother with MMA" verdict holds **only at K_PAD=64**.
Raise k for quality and PV becomes the thing you have to fix.

That asymmetry points somewhere useful: **k should be kv-adaptive.** Short kv →
attention is cheap and mass is concentrated, k=64 is fine. Long kv → PV is relatively
free *and* quality risk is highest, so k=256–512. Note this is now *safe* to implement
via source-define specialization precisely because `0281c0a` folded `source_hash` into
the pipeline cache label — pre-fix, compiling two K_PAD variants in one process would
have collided exactly like the `bm=32`/`bm=64` bug.

### 1.7 E20 silently ignores the tuned `hc=16`

`step_kernel.rs:3335`:
```rust
let hc = crate::shaders::attention_gemm::TuneCfg::default().hc.min(STEP_NQ_HEADS);
```
`TuneCfg::default().hc = 4` (`attention_gemm/mod.rs:45`), but the production flag
default is **16** (`flags.rs:181`, shipped in `9957a81` as the BO optimum — PLAN.md:115:
*"hc=16 the optimum at EVERY kv, monotonic"*, +3.6% @100k, bit-identical).

E20 hardcodes `TuneCfg::default()` and never reads `DGQ_GEMM_ATTN_HC`. Consequences:

1. **E20 runs at hc=4 and leaves the BO win on the table.**
2. **The A/B was not apples-to-apples**: `bench-prefill-super` ran E17 at hc=16 (flag)
   vs E20 at hc=4 (hardcoded). This biases *against* E20 — so 1.19× is a floor, not a
   ceiling. Good news, but it means the number is not the one you think it is.
3. **Scratch waste**: with both flags on, `step_kernel.rs:5948-5955` sizes the S plane
   from the *flag* (hc=16) while the encoder uses 4 → 4× over-allocation (1.6 GiB vs
   0.4 GiB at 100k, and 100k is where memory pressure bites).

**Landmine for whoever fixes this:** `hc` is hardcoded at **four** coupled sites —
`3335` (encoder) and `5984`/`5993`/`6002` (P/Idx/lrow scratch). Change only the
encoder and the scratch buffers overflow. Same coupled-constant shape as the
`tunable_wide_n_tile: 64` grid/compile pin already flagged in PLAN.md:104, and the
same shape as the `bm>32` bug itself. Worth a debug-assert tying encoder hc to the
allocated hc.

## Part 2 — int8 MoE disproof (`86acced`)

**Verdict: the dead end is SOUND — do not re-test. But the headline number is
inflated (9× → honest 5.6×) and the recorded *mechanism* is wrong in a way that will
mislead the next attempt.**

The audit reproduced the kernel standalone and hit **0.438 TFLOP/s vs their reported
0.43**, and **9.70× vs their 9×** — so the numbers below are directly comparable, not
a different experiment. The harness is honest: same `RouteScratch`/`BlockGroupedJob`,
same BM/BN/BK, same 4-simdgroup 2×2 layout, same `gflops()`, same shapes/slots/warmup
as the baseline (`bench_gemm.rs:660-760` vs `:770+`). Correctness-first discipline is
real (oracle-gated). **The harness is not the problem.**

### 2.1 Decomposing the 9.7×

Isolating one variable at a time (identical tile geometry, bit-identical outputs):

| Factor | Measured | Verdict |
|---|---|---|
| **Loop nest / no register blocking** | **1.72×** | **Real implementation flaw** |
| int32 mul vs f32 mad, same nest | 2.22× | Hardware — intrinsic to int8 |
| simdgroup MMA vs scalar f32 | 2.54× | Hardware — real MMA advantage |

1.72 × 2.22 × 2.54 = **9.7** — the measured gap, fully accounted for.

**The one real flaw: the inner loop is an inner-product nest, not an outer product.**
At `gemm_int_sparse.metal:171-189`, `a4`/`w0`/`w1` are all loaded *inside* the
innermost k-loop, so operands are re-fetched from tgmem per `(i,j)` pair. The
production path it's benched against does the opposite — `gemm_frag_tile.metal:46-68`
hoists `A[TM]`/`B[TN]` into registers per k-chunk then runs a TM×TN outer product.
**384 vs 80 tgmem loads per lane per BK=32.** Register-blocking the int8 kernel (same
math, bit-identical output) measured **0.755 vs 0.438 TFLOP/s = 1.72×**.

This directly contradicts the commit's own claim: *"Tile sweep (BM=32/64, BN=64/128)
did not close the gap — the loss is in the inner accumulation, not tiling."* They
swept tile *geometry* (2 points; BK never swept) but never the loop *nest* — the one
axis where the prototype differs from its own baseline.

### 2.2 The recorded physics is a coincidence-fit

`ARCHITECTURE.md:424-426` asserts *"the half-MMA's per-instruction width dominates the
int8 dot's per-lane scalar chain by ~9x, exactly the measured gap."*

Measured, **MMA is worth only 2.54×** over an identical scalar-float nest — not 9×.
The "512 MAC/simdgroup-inst vs 4 MAC/lane/inst" arithmetic implies ~4× from width
alone and *cannot* produce 9×. It matched only because it silently absorbed their own
1.72× bug plus a 2.22× int-mul penalty they never identified.

**The real mechanism they missed: int32 multiply is 2.2× slower than f32 mad on M3.**
That — not MMA width — is the specifically-int8 penalty, and it's the fact worth
keeping.

This is worth flagging loudly given this repo's own `DGQ_MOE_PREFILL_BM` fake-win
lesson (PLAN.md:104). **A just-so physics story that "matches exactly" is precisely
the failure mode to distrust** — here it matched because three errors multiplied to
the right answer. The standing lever-hygiene note should probably absorb this as its
second instance: *a mechanism that predicts the measured number is not thereby
validated; it can be right-for-wrong-reasons by construction.*

### 2.3 My own brief's premise was false — worth recording

I briefed the audit on the hypothesis that packed `dot(char4, char4)` was an available
fast path left on the table. **It isn't.** Probing the runtime compiler directly on
this M3 Pro: `dot(char4,char4)`, `simd_dot_acc_int8`, and `dot_product_4x8_packed` are
all **rejected**; only float `dot()` compiles. The kernel's manual 4-scalar expansion
at `:181-184` was the *only* expressible formulation. There is no DP4A-style primitive
in MSL to recover the gap, and no unpack-hoisting fix (the int8 path has no unpack at
all).

Note the provenance: `0d41267` upgraded this redirect to PROMISING on the premise that
*"the integer DOT-PRODUCT instruction (DP4A-style, family 7+) DO exist"* — factually
wrong. That text no longer exists at HEAD (PLAN.md was rewritten by the E18-sliding
work), so there's nothing to fix, but **the false premise is what made the whole
redirect look promising in the first place.** Worth remembering that the redirect cost
real time on a hardware claim nobody probed until now — a 20-line compile probe up
front would have killed it.

### 2.4 What to correct

The conclusion survives its flaws with room to spare — a *perfectly* register-blocked
int8 kernel is still **5.6× slower** than production, nowhere near the 1.0× kill
criterion; the two residual factors (2.22× int-mul, 2.54× MMA) are hardware properties
no restructuring addresses; int4 is deader still. `ARCHITECTURE.md:413` correctly
scopes to lever-family + regime and doesn't overclaim "int8 is impossible."

Two edits worth making:

1. **The bar is 5.6×, not 9×.** `ARCHITECTURE.md` tells a future attempt it *"has to
   clear the 9x bar."* Anyone who register-blocks the kernel will measure a 1.7× win
   **against a strawman** and mistake it for progress toward a bar that was never
   really there.
2. **Replace the mechanism**: int32-mul (2.2×) + MMA width (2.5×), not "MMA width ≈ 9×."

Minor, and it cuts *against* int8 anyway: int8 W is K bytes/row vs q4's ~K/2, so the
prototype reads ~2× the weight bytes of the baseline — a bandwidth penalty independent
of the math, material at rpe=16 (denoise, small-M). The bench emits per-regime rows but
both docs collapse to one headline.

No profiler/assembly/spill check was done, but in practice benign — all variants report
`maxTotalThreadsPerThreadgroup=1024`, so the header's unverified claim at `:12` ("int8
has no MMA register-pressure trap") happens to hold.

## Part 3 — KV rewind corruption fix (`632aa69`)

**Verdict: INCOMPLETE. The diagnosis is right and the rebuild is genuinely
bit-identical to a fresh prefill, but the wrap predicate is off by CANVAS (same bug,
narrower window), a duplicate truncate-then-extend path is unfixed, the added test
cannot fail without the fix, and it introduces a severe unmeasured perf regression.**

This is the one I'd act on first — it's a live correctness bug, not a perf question.

### 3.1 What's solid

- Ring design confirmed: 2048 slots (`step_kernel.rs:504`, `slot = pos & 2047`),
  window 1024 (`:3553-3554`), CANVAS=256 (`:55`).
- **The rebuild is bit-identical to a fresh prefill.** `extend_kv` →
  `prefill_chunks_from(0, kept)`, and `prefill_chunks(t)` is literally
  `prefill_chunks_from(0, t)` (`step_kernel.rs:4833-4835`). Chunking is a function of
  `(offset, len)` only.
- Failure modes are fail-safe: `reset_kv()` precedes `extend_kv`, capacity check fires
  before any write → a failed rebuild leaves an empty KV (slow), never half-written.
- Clean edges: `new == old` early-returns; `new == 0` → `reset_kv()`; double-truncate
  is a no-op; `ring = None` never rebuilds (linear slots are never aliased);
  `max_seq ≤ 2048` provably never wraps.

### 3.2 The predicate is off by CANVAS — corruption remains

`step_generate.rs:258-264`:
```rust
new_len < old_len && ring.is_some_and(|r| old_len > r)
```

`old_len > ring` tests the highest **committed** position. But denoise canvas writes
land at `[kv_len, kv_len+256)` **unconditionally** (`kv_write_end = u32::MAX`,
`:186-195`) — up to 255 positions past `old_len`, committed or not. So the ring can
already have wrapped while the predicate says "safe."

Verified repro shape (needs `max_seq > 2048`, i.e. serve/chat at 4096/8192): last
denoise block at `kv_len=2000` writes positions 2000–2255 → slots 0–207 now hold
positions 2048–2255. Block stops on EOT → never committed → `old_len = 2000`, and
`2000 > 2048` is false → **no rebuild**. `finalize` truncates to 1200 → needed window
is `[177, 1200]` → **positions 177–207 are canvas junk.** Same alpha-soup vector.

I ran the predicate against a from-first-principles corruption model over the boundary:

| old | new | actually corrupt | current | proposed |
|---|---|---|---|---|
| 2048 | 100 | **true** | **false** ← misses | true |
| 2000 | 1200 | **true** | **false** ← misses | true |
| 1900 | 1000 | **true** | **false** ← misses | true |
| 2049 | 100 | true | true | true |
| 30000 | 29999 | false | **true** ← needless 30k re-prefill | false |

**The new test enshrines the hole.** `step_generate_tests.rs:42`:
```rust
assert!(!kv_truncate_needs_ring_rebuild(2048, 100, Some(2048)));
```
commented *"Below wrap — early slots were never overwritten."* That comment is false —
at `old_len=2048` the canvas wrote positions 2048–2303 into slots 0–255, and truncating
to 100 needs exactly those slots. **This asserts the corrupt case is safe.**

**One predicate change fixes both the correctness hole and the perf regression.** The
ring holds the last `ring` *written* positions; a truncate to `new` needs down to
`new - (window-1)`:

```rust
let Some(ring) = ring else { return false };
if new_len >= old_len { return false; }
// Denoise canvas writes land at [kv_len, kv_len+CANVAS) even when the block is
// never committed, so the highest WRITTEN position is old_len + CANVAS - 1.
let oldest_live    = (old_len + CANVAS).saturating_sub(ring);
let deepest_needed = new_len.saturating_sub(WINDOW - 1);
deepest_needed < oldest_live
```

This is **necessary and sufficient** — exact on every row of the table above. Note the
`saturating_sub`s are load-bearing: the raw inequality
`new_len < old_len + CANVAS + WINDOW - 1 - ring` (as first derived) over-rebuilds below
the wrap — e.g. `(1000, 100)` isn't corrupt but the unsaturated form says rebuild.

### 3.3 The same truncate-then-extend exists unfixed in `generate_with_session`

`step_generate.rs:650-659` — verified directly:
```rust
} else if reuse > 0 {
    let delta = &prompt_token_ids[reuse..];
    let kv_len = ... rt.prefill_chunks_from(reuse, delta)?
```
When `reuse < kv_valid_tokens.len()` this **is** a downward truncate + extend — keeps
`KV[0..reuse)`, re-prefills at that offset — and it never calls `truncate_kv_to` nor
checks the ring. Past a wrap, the delta prefill at `p = reuse` reads window
`[reuse-1023, reuse)` from **stale slots**, so even the freshly-written delta is
computed from poisoned context.

Exposure:
- **serve is mostly shielded** — `route()` requires `prompt.starts_with(c.tokens)`
  (`conversation.rs:87-93`) so `reuse == kv_valid_tokens.len()`.
- **`chat` CLI is not** — `CHAT_MAX_SEQ` = 8192 (`commands/chat.rs:82`), no
  conversation manager, `kv_valid_tokens` = prompt + committed *raw* blocks while the
  next prompt carries the *sanitized* reply. Any reply > 256 tokens (≥1 committed
  block) whose sanitization strips anything (thought channel, degenerate ids) diverges
  → partial reuse → poisoned ring past 2048 tokens.
- **`run_summarize_pass`** (`server.rs:801-802`) drives `generate_with_session` with a
  deliberately *divergent* prompt on the routed session — straight into this path.
  That's the tool-compaction rewinder, i.e. exactly the feature this KV machinery
  exists for.

Stale doc found in passing: `server_tool_smoke_tests.rs:43` claims
*"`generate_with_session` resets the KV when the prompt doesn't extend it."* False —
`reset_kv_unless_extends` (`step_generate.rs:534-539`) is `#[allow(dead_code)]` and
called from nowhere.

Also `:640-649` + `:739`: the `existing_kv >= n_prompt` branch moves `kv_len` down via
`set_kv_len` with no ring check and no verification that the prompt matches the
resident tokens. Shielded in serve by `route()`; reachable elsewhere.

### 3.4 `rollback_to`'s contract is violated by its only production caller

`rollback_to` assumes the KV only grew by *causal appends* since the checkpoint.
`run_summarize_pass` (`server.rs:801-808`) checkpoints, generates a **divergent**
prompt (re-prefilling at an offset *below* `cp.tokens`), then rolls back — so
`kv_valid_tokens[..tokens]` (`:415`) is a prefix of the *summarize* sequence, not the
checkpointed conversation. The rebuild makes the state internally *consistent* rather
than merely stale, so it's an improvement, but "rollback restores the conversation" is
still false. The subsequent main generate self-heals the log via LCP — and lands back
in §3.3.

Minor: the rebuild branch ignores `cp.kv_len` entirely (kv_len ends at `cp.tokens`)
while the clamp branch uses `cp.kv_len.min(old)` — divergent if the two disagree.

### 3.5 Severe unmeasured perf regression

The rebuild is a **full re-prefill of the kept prefix from token 0**, and the predicate
fires on `old_len > 2048` *regardless of truncation size*. Combined with `finalize`'s
`truncate_kv_to(reuse)` + `extend_kv(tail)` (`conversation.rs:342-343`), **a 1-token
truncation at 30k context costs a full 30k re-prefill (~98s per project memory)** —
precisely what cross-turn KV reuse exists to avoid (turn-3 2.96→0.86s,
memory `cross-turn-kv-reuse`).

Not hypothetical: after a >256-token reply, `kv_valid_tokens` = prompt + committed raw
blocks, `reuse` = LCP vs the sanitized canonical → `reuse < old` on **every long agent
turn**. Short replies (single uncommitted block) hit `n == old` and stay free.

The §3.2 predicate makes truncations of ≤769 tokens free at any context length —
closing the correctness hole and recovering most of the perf in one change. Beyond
that there's no cheaper rebuild: recomputing sliding K/V at `[n-1023, n)` needs hidden
states, which need attention over prior KV, recursively. (A ring shadow-copy at
checkpoint — 2048 slots × 25 sliding layers ≈ a few hundred MB — is the only O(copy)
alternative.)

### 3.6 No test reproduces the bug

- `step_generate_tests.rs:36-49` is a **tautological restatement of the predicate** —
  it calls the free function with literals. Delete the call sites in
  `truncate_kv_to`/`rollback_to` and **it still passes.** It tests that `>` means `>`.
  And `:42` bakes in the §3.2 hole.
- `server_tests.rs:92`/`:135` are channel-markup tests, unrelated to KV.
- `server_tool_compact_tests.rs:145,173` are mechanical `.unwrap()` additions; that
  test only asserts `kv_valid_tokens()` (the *token log*) — never KV bytes or output —
  so it's structurally incapable of catching ring poisoning.

**Golden was not re-blessed**, which means the golden matrix never reaches the rebuild
branch — the Tier-1 gate does not cover this change at all. (The rebuild is
bit-identical to a fresh prefill but *not* to the old clamp path below the hole:
positions previously written by committed denoise blocks are now prefill-written.)

The repo already has the right vehicle: `step_kv_bench_tests.rs:276`
`engine_hydrate_ring_exactness` does byte-level ring verification. A real test =
prefill/denoise past 2048 → `truncate_kv_to(n)` → compare live-window KV bytes against
a fresh session prefilled to `n`. **That test would fail without the fix, and would
also fail today at `old_len ∈ (1792, 2048]`.**

### 3.7 FIXED 2026-07-16 (tasks #91, #92) — and what the oracle turned up

**§3.2 predicate: fixed.** `kv_truncate_needs_ring_rebuild` now takes `window` and
returns `deepest_needed < oldest_live` with saturating subtraction (see
`step_generate.rs`). Two unit tests:

- `kv_truncate_needs_ring_rebuild_matches_corruption_model` — checks the predicate
  against an **independently derived** corruption model (written from the storage rule
  only, sharing no code with the predicate) across `old ∈ 0..6000` × 10 `new` values.
  It immediately caught my own hand-written boundary being off by one (the true edge is
  `old-769`, safe at `new = old-769`), which is exactly the job a non-tautological test
  is supposed to do.
- `kv_truncate_needs_ring_rebuild_policy` — the named cases, now including the three
  the old predicate called safe and the two shallow-truncation perf cases.

**§3.6 oracle: built, and it fails pre-fix — with the exact predicted signature.**
`truncate_after_uncommitted_canvas_write_matches_fresh_prefill` drives the ordinary
production flow (prefill 2000 → generate a short reply, whose final block writes canvas
at `[2000,2256)` and never commits → `truncate_kv_to(1200)`) and compares
`snapshot_kv` against a fresh prefill of the same 1200 tokens. Reverting to `632aa69`'s
predicate:

```
truncate_kv_to(1200) ... left 208 of 1200 layer-0 ring slots differing from a fresh
prefill (slots Some(0)..=Some(207)) — poisoned slots survived into the live window
```

**208 slots, 0..=207** — precisely the canvas write of positions 2048..=2255 landing in
wrapped slots, as predicted from the storage rule in §3.2. Post-fix it passes.

**The oracle could not be a whole-KV compare — and finding out why was the most
valuable part.** The premise control (two identical `reset_kv` + `extend_kv` cycles →
identical KV) **failed**: ~80% of bytes differed, and differed *again* on a third run,
ruling out "deterministic function of stale buffer residue". Layer 0 was always
bit-identical while layers 1..29 diverged from slot ~14 — i.e. layer 0's *KV* is
reproducible (it is a pure function of `embed(tokens)`) but its *attention output* is
not, and that amplifies through depth. **This is pre-existing and unrelated to the fix**
(the control calls neither `truncate_kv_to` nor `rollback_to`). See task #99. The oracle
therefore asserts on **layer 0 only** — still a ring layer, so still poisoned by the
identical mechanism — with `layer0_prefill_kv_is_bit_reproducible` as the documented
premise control. Widen it when #99 lands.

**Verification:** suite 581/1, golden 3/8 — **both identical on clean HEAD**, so this

## Part 4 — E18 sliding flash: a race and a cache collision (found + fixed 2026-07-16)

Chasing the nondeterminism the §3.7 oracle exposed (task #99) turned up **two** bugs in
E18 sliding flash — both instances of classes this repo has already fought once.

### 4.1 Missing threadgroup barrier — the nondeterminism

`attention_flash.metal` stages `Qs` strided by `tid`
(`for (uint i = tid; i < BQ*hd; i += TPG)`), then **every simdgroup** reads the whole
tile via `simdgroup_load` in the QK step. There was **no `threadgroup_barrier` between
the staging loop and the first read** — the first barrier sat at the *end* of the QK
step, too late. The first K-block iteration raced the staging; later iterations were
covered by the barrier closing the K-block loop. Only the first read was exposed. Same
class as the SC GEMM "missing gemm_b barrier" (memory `sc-gemm-nondeterminism`).

**Fix:** one barrier after staging, before the loop.

| `prefill_nondeterminism_probe` (3× `reset_kv`+`extend_kv(1200)`) | A-vs-B | B-vs-C |
|---|---|---|
| flash ON, pre-fix | 216182753 | 212327667 (of 270336000 ≈ **80%**) |
| flash OFF (the bisect) | **0** | **0** |
| flash ON, post-fix | **0** | **0** |

End-to-end: `golden`'s longctx_13k emitted **13065 then 13067** tokens on consecutive
runs of the same binary+seed pre-fix; post-fix two full golden runs are byte-identical.

**Why layer 0 was always clean** — the clue that localized it: layer 0's K/V is a pure
function of `embed(tokens)`, written *before* attention runs, so it stayed bit-identical
while layer 0's attention *output* raced and amplified through depth.

**Perf: free.** A/B on `flash_bench_hd256` (bq16), kv 8192/30000/60000: with barrier
33.07/121.81/255.61 ms vs without 35.14/133.08/260.51. It is once per threadgroup, not
per K-block iteration; the delta is inside the bench's own ~5% noise (the `e17` baseline
column moved 15.7→16.6 across the same two runs).

**Correction to my own reasoning, recorded because it nearly misled the diagnosis:** I
claimed "B≠C rules out a deterministic function of stale buffer residue." **Wrong** —
each round's residue *is* the previous round's output, so a deterministic kernel reading
stale KV also yields B≠C. The flag bisect is what actually discriminated, not the 3-way
compare.

### 4.2 Pipeline-cache label collision — `0281c0a`'s class, in a second kernel

`flash_gpu_full_grp8_causal_vs_cpu` failed **in-suite but passed in isolation, on clean
HEAD**. `pipeline_flash` bakes `FL_HD/FL_BQ/FL_BK` into the **source** via
`tuned_source(bq,bk,hd)` but passes the constant literal `"flash"` as the cache label.
`PipelineArchiveCache` dedupes **by label**, so hd=256 (sliding, production) and hd=512
(full, the test) shared one — whichever compiled first won, and E18's own hd=512 oracle
was being validated against the hd=256 pipeline. `attention_gemm`'s `"tune"` label has
the identical defect. And `extra_bools`/`extra_uints` are real specializations that
never reached the label at all; call sites encode them **by convention**
(`"side"`/`"default"`, `fmt.label()`) — one forgotten string from a silent miscompile.

This is exactly what `0281c0a` fixed for GEMM (source-baked `TUNE_BM` absent from the
label → a `bm=32` kernel ran for `bm=64` and zeroed half the rows). **That fix hashed
the source into the *GEMM* label only.** The memory note claims it "closes the whole
class of source-define collisions" — it didn't; `compile_subkernel_ex` has its own
labeling and was untouched.

**Fix** (`device.rs`, `compile_subkernel_on_device`): fold `source_hash(source)` **plus
every extra FC index/value** into the label, closing the class for every caller rather
than one kernel. Deriving the label from the actual inputs beats remembering to pass a
distinguishing string.

**Production impact: none** — production compiles only the hd=256 sliding variant, so
nothing collided. It was corrupting *tests*, including the oracle meant to validate E18.
That is its own lesson: **the collision silently weakened the gate that was supposed to
catch it.**

### 4.3 Verification

Suite **582/0** (was 581/1 — that failure was §4.2). Golden 3/8 **unchanged** and now
stable across runs; still red for an unrelated reason (task #100, E18 shipped
non-bit-identical and was never re-blessed — now unblocked, since blessing a
nondeterministic case was the thing to avoid).

## Part 5 — the red golden gate: root-caused + re-blessed → 8/8 (task #100)

**Two causes, both intentional. Neither was an engine regression** — and the second one
is a trap worth remembering.

### 5.1 E18 explains two of five

`DGQ_FLASH_PREFILL=0` takes golden 3/8 → **5/8**: `cross_turn_reuse` and
`multi_block_reply` (the "KV hash differs, token_ids identical" pair) pass. That is E18
sliding flash (`42de5cd`), non-bit-identical by design, signed off on smoketest
17/17×{7,42,123} + longctx 4/4, never re-blessed. Hypothesis confirmed — but only half.

### 5.2 The other three: a *correct* decode fix, and a gate that gates its own harness

The remaining three (`fast_prefill_3k`, `ring_wrap_2p5k`, `longctx_13k`) fail with flash
off, identically at `index 237: golden=17723 got=138`. Bisected to **`83b184e`**
(`fix(serve): harden OpenCode tool path, thinking defaults, and decode indent`); parent
`466cee4` = 8/8.

**Mechanism, proven by code rather than inferred** — `src/commands/golden_cmd.rs:269-271`:

```rust
let ids = &doc_cache[doc];                    // encode longdoc.md
let n = case.doc_tokens.min(ids.len());
let excerpt = tokenizer.decode(&ids[..n]);    // <-- DECODE round-trip
let prompt_text = format!("{excerpt}\n\n[end of document]…");
let prompt = build_chat_prompt_tokens(…)?;    // <-- re-encode
```

The doc cases build their prompt **encode → truncate → decode → re-encode**, so
`tokenizer.decode` sits *on the golden prompt-construction path*. `83b184e` correctly
changed decode from "collapse a leading `▁` run to ONE space" to "replace EVERY `▁` with
a space", matching `tokenizer.json`'s Replace decoder (with a regression test:
`"    return"` → `[140, 2060]` → `"    return"`). The old behaviour destroyed
indentation (`▁▁▁▁`, id 140 → one space) — precisely the bug that broke OpenCode tool
writes.

**So the blessed prompts encoded the decoder bug.** Index 237 is *inside* the prompt
(prompt_len=3005), not the generation.

The bless diff confirms this independently of the bisect:

| case | prompt_len | |
|---|---|---|
| `fast_prefill_3k` | 3005 → 3038 | **+33** |
| `ring_wrap_2p5k` | 2505 → 2538 | **+33** |
| `longctx_13k` | 12834 → 13040 | **+206** |
| `engine_prefill`, `early_stop_off`, `tool_call` | — | unchanged |
| `cross_turn_reuse`, `multi_block_reply` | — | kv_hash only |

The 3k and 2.5k docs share their leading ~3000 tokens and move by *exactly* the same
+33; the 13k doc moves +206 — proportional to how much indentation is restored. That is
the decode mechanism, measured.

### 5.3 Re-blessed, in the right order

Gates run **before** blessing, per the documented policy: smoketest **17/17**, longctx
**4/4** (8/8 keywords, drift 0.0%), suite 582/0. The determinism precondition was met by
§4.1 — pre-fix, `longctx_13k` emitted 13065 then 13067 tokens on the same binary and
seed, so blessing then would have frozen one sample of a random variable and made the
gate flaky forever. Result: **8/8, stable across two subsequent runs.**

The new baseline encodes: the correct `▁` decode (`83b184e`), E18 default-on
(`42de5cd`), and this session's fixes (§4.1 barrier, §4.2 cache label, §3.7 ring
predicate). **Coupling: the bless must land together with the §4.1 barrier fix** —
blessing without it freezes racy flash output. If that fix is ever reverted, golden
going red is *correct*.

### 5.4 Two lessons

1. **A gate whose harness round-trips through the code it gates will restale itself on
   any correct fix to that code.** golden's doc prompts are decode-dependent, so *any*
   decoder change moves them — and it looks exactly like an engine regression
   (`token_ids diverge`). Worth a line in the golden README.
2. **Self-test a bisect predicate against a known-bad commit before trusting the run.**
   My first script grepped for the case *name* — which golden prints on PASS lines too
   (`fast_prefill_3k  OK …`) — so every commit tested "bad" and bisect returned the
   oldest candidate by construction. That candidate, `11bc846`, was *superficially
   perfect*: the commit that made E17's tile geometry tunable. I nearly wrote it up.
   Two things caught it: reading the diff (at the defaults `constant uint BM = 64u` →
   `#define AG_BM 64` + `constant uint BM = AG_BM` is semantically identical, so it
   *couldn't* change numerics), and verifying that commit and its parent directly —
   both 8/8. Same discipline as §2.2: a mechanism that sounds right is not evidence.

## Cross-cutting

Three observations that span all three threads:

1. **Tests that can't fail.** The KV predicate test (§3.6) and E20's exactness claim
   (§1.5) both assert something other than what the code does. Both would pass on
   broken code. This is the same shape as the `sparse_block_m_invariant` lesson from
   `0281c0a` — the fix there wasn't the kernel, it was building an oracle that could
   *see* the bug. Neither of these commits has that oracle.

2. **A mechanism that "matches exactly" is not thereby validated** (§2.2). The int8
   physics story predicted 9× and got 9× — by multiplying a 1.72× own-bug, a 2.22×
   effect nobody identified, and a 2.54× effect credited with the whole gap. PLAN.md's
   lever-hygiene note already says a speedup without a correctness oracle isn't a
   vindication; the dual is worth adding: **a disproof whose stated mechanism was never
   independently measured isn't a mechanism, it's a curve fit.** Both instances now
   come from the same campaign.

3. **Coupled constants keep biting.** `hc` at four sites (§1.7), `tunable_wide_n_tile`
   grid-vs-compile (PLAN.md:104), the `bm=32`/`bm=64` cache label (`0281c0a`), and now
   the flash `"flash"`/`"tune"` labels (§4.2) are all the same failure: a value that must
   agree across two places with nothing enforcing it. Each was found by a person, not a
   check. §4.2's fix is the general shape of the answer — **derive the key from the
   actual inputs instead of asking callers to remember a string.**

4. **A fix scoped to one call site does not close a class.** `0281c0a` hashed the source
   into the *GEMM* cache label and the memory note recorded it as closing "the whole
   class of source-define collisions." It didn't — `compile_subkernel_ex` had its own
   labeling, and E18 walked straight into the identical bug two weeks later (§4.2). When
   a root cause is a *pattern*, the fix and the write-up should both name every site the
   pattern reaches, or say plainly which ones were left.

5. **Tools need self-tests too, not just code.** §5.4's bisect predicate and §2's int8
   "physics" failed the same way: both produced a confident, plausible answer that was
   an artifact of the instrument. The bisect even printed its own giveaway (`OK` right
   before "first bad commit") and I read past it. Before trusting a measurement
   apparatus, run it against a case whose answer you already know.

6. **Three of this session's bugs were invisible to the gates that cover those exact
   paths** — the ring truncate (golden's cases never wrapped past a *canvas* write), the
   flash race (golden was already red, so nobody looked), and the flash cache collision
   (which corrupted the very oracle meant to validate E18). The gates weren't missing;
   they were red, blind, or self-undermined. **A red Tier-1 gate is worse than no gate:
   it reads as "known red, ignore," and then it stops reporting new breakage.** Getting
   golden back to green (#100) is worth more than any single fix in this document.
